# Разбиение изменений на серию логических коммитов

## Обзор

Когда в рабочем дереве накопилось много правок разного назначения, не делай один
огромный коммит. Разбей `git diff` на небольшие логические группы и создай
отдельный коммит на каждую группу, соблюдая правила Conventional Commits.

Формат сообщений и правила типов — в навыке `commit` (этот навык только про
сегментацию и последовательное применение).

## Когда использовать

- В `git status` много файлов с несвязанными правками (фича + баг + доки).
- Пользователь просит «закоммитить по частям», «разбить на коммиты», «сделать
  несколько коммитов».
- Одна правка уже явно содержит разные `type` (feat + fix) или разные `scope`
  (frontend + backend).

### Когда НЕ использовать

- Изменения — единая атомарная правка → обычный `commit`.
- Пользователь явно хочет один коммит со всем сразу → `commit`.

## Порядок работы

1. **Осмотрись.** Выполни `git status`, `git diff`, `git diff --staged` и
   `git log --oneline -10`, чтобы понять объём и стиль истории.
2. **Сегментируй по намерению.** Сгруппируй изменения так, чтобы один коммит =
   одно логическое намерение с одним `type`(и `scope`). Критерии разбиения:
   - разные `type`: `feat` / `fix` / `docs` / `refactor` / `test` и т.д.;
   - разные `scope`: `frontend` против `backend` (в этом монорепо не смешивай
     их в одном коммите без необходимости);
   - независимые фичи или разные баг-фиксы;
   - тесты/документация, относящиеся к отдельной правке.
3. **Определи порядок.** Сначала коммить то, от чего зависят другие правки:
   конфиги/сборка/зависимости (`build`, `ci`), затем сама логика (`feat`,
   `fix`, `refactor`), отдельно `test` и `docs`.
4. **Для каждой группы:**
   - сделай staging только нужных файлов/путей: `git add <files>` (или
     `git add -p <file>` для частичного включения одного файла);
   - сформируй сообщение по правилам `commit`;
   - `git commit -m "<type>(<scope>): <subject>"` (body/footer через `-m`,
     если нужно).
5. **Не нарушай безопасность.** Никогда не коммить секреты и `.env`. Не
   используй `--amend`, `--no-verify`, force-push и пустые коммиты, если
   пользователь явно не попросил. Если хук отклонил — исправь и сделай новый
   коммит.
6. **Проверь результат.** После каждого коммита `git status` и `git log -1`
   должны подтверждать, что добавилась ровно одна логическая правка. В конце
   `git status` показывает, что осталось незакоммиченным. Push — только по
   явной просьбе.

## Пример сегментации

Допустим, `git diff` содержит: новый эндпоинт в backend, правку nil-проверки в
backend, правку README и новый тест frontend-формы.

```
group 1 (backend, feat):     новый эндпоинт            -> feat(backend): add export endpoint
group 2 (backend, fix):      nil-проверка              -> fix(backend): handle nil in export builder
group 3 (frontend, test):    тест формы                -> test(frontend): add export form validation
group 4 (docs):              README                    -> docs: document export endpoint usage
```

Коммитим группы по очереди, staging только соответствующие файлы.

## Частые ошибки

- Один коммит на всё («закоммичу потом разберём») — теряется смысл истории.
- Смешивание frontend и backend в одном коммите — ломает изоляцию монорепо.
- `git add .` / `git add -A` целиком — в коммит попадают чужие и секретные
  файлы.
- Разрыв связной правки между двумя коммитами (например, код без его тестов) —
  каждый коммит должен оставлять проект в рабочем состоянии.
- Тип, не соответствующий сути (например `chore` для новой фичи).

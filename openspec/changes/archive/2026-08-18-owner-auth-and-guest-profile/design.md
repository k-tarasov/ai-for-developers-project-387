## Context

Бэкенд — Go, фронтенд — React 19, контракт — `spec/main.tsp` (TypeSpec → OpenAPI). Сейчас владельческие эндпоинты открыты, а гость не имеет профиля: каждое бронирование заново передаёт имя/контакты. Нужно добавить аутентификацию владельца и профиль гостя поверх существующего контракта, не ломая сценарии гостевого бронирования.

## Goals / Non-Goals

**Goals:**
- Расширить `spec/main.tsp` новыми моделями, интерфейсами `Auth`/`Guest` и ошибками; закрыть владельческие эндпоинты сессией.
- Описать хранение статических учётных данных владельца, выдачу/проверку сессий владельца и `guest_id`-куки, лимит попыток входа, хранение профиля гостя.
- Описать фронтенд-навигацию: главная (профиль гостя) → список событий → компонент события (инфо/календарь/слоты/комментарий).

**Non-Goals:**
- Реальное хеширование паролей и полноценная система пользователей (данные статические, заданы при старте).
- Регистрация/восстановление пароля владельца.
- Многосессионность/выход владельца (в рамках MVP сессия — только установка cookie).

## Decisions

- **Статические учётные данные владельца** задаются при старте бэкенда через env-переменные (например, `OWNER_LOGIN`, `OWNER_PASSWORD`) или флаги. В MVP сравниваются по точному совпадению (constant-time compare).
  - *Альтернатива*: файл конфигурации. Env выбран как самый простой для старта и CI/mock.
- **Сессия владельца** — случайный токен, выдаваемый в httpOnly cookie (`owner_session`) при успешном `POST /auth/login`. Владельческие эндпоинты проверяют наличие и валидность токена → иначе `401`.
  - *Альтернатива*: Bearer-токен в заголовке. Cookie выбран, чтобы фронтенд не хранил токен в JS и не тащил его вручную.
- **Идентификация гостя** — `guest_id` в httpOnly cookie. `POST /guest` либо создаёт нового гостя, либо (если cookie уже есть) обновляет её; возвращает `guest_id`. При `rememberMe=true` cookie выдаётся со `Max-Age=30d`, иначе сессионная. `GET /guest` читает cookie и возвращает профиль или `404 GUEST_UNKNOWN`.
  - *Альтернатива*: токен в заголовке (отвергнут — см. ответ пользователя: httpOnly cookie).
- **Лимит попыток входа** — счётчик неудачных попыток по IP (или по логину) с окном блокировки; при превышении `POST /auth/login` отвечает `429 LOGIN_ATTEMPTS_EXCEEDED`. Сброс счётчика при успешном входе.
- **Хранение профиля гостя** — в бэкенде (in-memory для MVP, как и остальные сущности сервиса) с ключом по `guest_id`: имя, `guestPhone?`, `guestEmail?`.
- **Комментарий гостя** — поле `guestComment` уже есть в `BookingCreate`; компонент события добавляет textarea, значение которого попадает в `POST /bookings`. Спецификация `main.tsp` не меняется для бронирования, только используется.

### Изменения в `spec/main.tsp`

- Новые модели: `OwnerLogin { login, password }`, `AuthSuccess { ok: true }` (cookie устанавливается ответом), `GuestProfile { id, name, guestPhone?, guestEmail? }`, `GuestCreate { name, guestPhone?, guestEmail?, rememberMe: boolean }`.
- Новые ошибки: `UnauthorizedError` (`401`, коды `INVALID_CREDENTIALS` | `NO_OWNER_SESSION`), `LoginThrottledError` (`429`, код `LOGIN_ATTEMPTS_EXCEEDED`), `GuestUnknownError` (`404`, код `GUEST_UNKNOWN`).
- Интерфейс `Auth`: `POST /auth/login` → `200` + cookie | `401 INVALID_CREDENTIALS` | `429 LOGIN_ATTEMPTS_EXCEEDED`.
- Интерфейс `Guest`: `GET /guest` → `GuestProfile` | `404 GUEST_UNKNOWN`; `POST /guest` → `201 GuestProfile` | `400 VALIDATION_ERROR`/`CONTACT_REQUIRED`; `PUT /guest` → `GuestProfile` | `404 GUEST_UNKNOWN`.
- Владельческие эндпоинты (`EventTypes.create/update/delete`, `Schedule.get/update`, `Bookings.list`) дополняются ответом `401 NO_OWNER_SESSION` (через `UnauthorizedError`).

## Risks / Trade-offs

- [Статический пароль в env] → В MVP приемлемо; позже заменить на секрет/хранилище. Не коммитить значения в репозиторий.
- [Сессия владельца в памяти] → при перезапуске бэкенда сессии сбрасываются, владельцу нужен повторный вход. Приемлемо для MVP.
- [httpOnly cookie и mock-сервер] → mock должен уметь выставлять cookie, иначе сценарии входа/гостя в mock-режиме невоспроизводимы. Учесть в задачах на mock.
- [BREAKING: закрытие владельческих эндпоинтов] → существующие вызовы без сессии перестанут работать; фронтенд-клиент должен добавить cookie автоматически (браузер) и экран входа.

## Migration Plan

1. Расширить `spec/main.tsp`, сгенерировать OpenAPI, обновить mock-сервер.
2. Бэкенд: учётные данные владельца, `/auth/login`, защита владельческих эндпоинтов, `/guest` CRUD + `guest_id`-куки, лимит попыток.
3. Фронтенд: клиент API с поддержкой cookie, экран входа владельца, загрузка `GET /guest` на главной, карточка/форма гостя, компонент события с комментарием.
4. Проверка в mock-режиме и против реального бэкенда.

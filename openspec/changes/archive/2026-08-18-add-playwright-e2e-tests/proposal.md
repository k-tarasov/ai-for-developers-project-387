## Why

Фронтенд приложения «Запись на звонок» покрыт только юнит/компонентными тестами (Vitest + Testing Library), но в репозитории отсутствуют сквозные (e2e) проверки поведения всего приложения целиком. Юнит-тесты не ловят регрессии на стыке «браузер ↔ бэкенд»: сессии (httpOnly cookie `owner_session` / `guest_id`), реальные сетевые запросы по контракту, навигация между страницами, состояние гостя/владельца после перезагрузки.

Цель изменения — добавить набор Playwright e2e-тестов, покрывающий все use-cases приложения (гостевой и владельческий потоки), запускаемых против реального бэкенда в памяти. Это даст уверенность в том, что ключевые пользовательские сценарии работают end-to-end после любого изменения.

## What Changes

- Добавляется директория e2e-тестов Playwright (например, `frontend/e2e/`) с конфигурацией, запускающей бэкенд и фронтенд в тестовом окружении.
- Покрываются все сценарии из спеки `frontend-app` и `booking-api` на уровне пользовательских действий в браузере.
- Добавляются вспомогательные фикстуры/хелперы (логин владельца, создание типа события, генерация слота, управление cookie `guest_id`).
- Настраивается npm-скрипт и/или Makefile-цель для запуска e2e.

## Impact

- Зависимости: `playwright` (devDependency в `frontend/`), при необходимости Playwright-браузеры.
- Инфраструктура: CI-шаг запуска e2e (добавить в `.github/workflows/hexlet-check.yml` нельзя — он авто-генерируемый; новый шаг через Makefile/отдельный workflow).
- Не затрагивает продакшен-код фронтенда и бэкенда (только добавление тестов).

## Список e2e-сценариев (use-cases)

Ниже черновой список проверок по всем use-cases приложения. Пожалуйста, проверьте и дополните его — после ревью перенесём в delta-spec и tasks.

### Гостевой поток (Guest)

**G1. Главная — список типов событий**
- G1.1. Главная страница показывает список типов событий (название, описание, длительность) из `GET /event-types`.
- G1.2. Пустой список типов → понятное пустое состояние без ошибки.
- G1.3. Ошибка/недоступность бэкенда при загрузке списка → сообщение о недоступности + кнопка повтора.

**G2. Профиль гостя**
- G2.1a. Новый гость (без cookie `guest_id`) при открытии видит список типов событий.
- G2.1b. После выбора типа события новому гостю показывается форма ввода данных (имя + контакт).
- G2.2. Знакомый гость (валидная cookie `guest_id`) видит карточку со своим именем и контактами.
- G2.3. Гость заполняет форму с `rememberMe=true` → после `POST /guest` становится «знакомым», cookie `guest_id` выдана.
- G2.4. Гость заполняет форму без `rememberMe` → сессионная cookie `guest_id`.
- G2.5. Отправка формы без телефона и без email → блокировка отправки, сообщение «нужен хотя бы один контакт».
- G2.6. Знакомый гость редактирует имя/контакт в карточке → `PUT /guest` сохраняет, карточка обновляется.
- G2.7. Ошибка `PUT /guest` → сообщение об ошибке, данные не считаются сохранёнными.
- G2.8. Перезагрузка страницы знакомым гостем → профиль подтягивается из `GET /guest` (cookie сохранена).
- G2.9. Ошибка загрузки профиля гостя (`GET /guest` недоступен) → сообщение о недоступности данных + кнопка повтора.
- G2.10. Ошибка создания профиля гостя (`POST /guest` возвращает ошибку, например `VALIDATION_ERROR`) → сообщение об ошибке, форма не очищается.

**G3. Просмотр слотов**
- G3.1. Выбор типа события → слоты загружаются (`GET /event-types/{id}/slots`) и сгруппированы по дням по возрастанию времени.
- G3.2. Пустой список слотов → сообщение об отсутствии свободного времени в окне записи.
- G3.3. Несуществующий тип события (404 `EVENT_TYPE_NOT_FOUND`) → сообщение, тип недоступен, предложение вернуться к списку.

**G4. Создание брони**
- G4.1. Знакомый гость выбирает слот, добавляет комментарий и отправляет → `POST /bookings` → экран подтверждения с типом события, временем начала и окончания. Имя и контакт берутся из профиля гостя.
- G4.2. Отправка формы бронирования без профиля гостя → кнопка отправки заблокирована до обращения к API.
- G4.3. Слот занят (409 `SLOT_BUSY`) → сообщение, предложение выбрать другое время с обновлённым списком.
- G4.4. Слот не проходит валидацию (400 `SLOT_MISALIGNED`/`SLOT_OUT_OF_WINDOW`/`SLOT_OUTSIDE_SCHEDULE`) → текст ошибки из API, предложение выбрать другой слот.
- G4.5. Гость добавляет комментарий → комментарий включается в `POST /bookings` (`guestComment`).

### Владельческий поток (Owner)

**O1. Аутентификация владельца**
- O1.1. Кнопка «Админка» открывает форму входа; корректные логин/пароль → `POST /auth/login`, устанавливается cookie `owner_session`, открывается интерфейс владельца.
- O1.2. Неверные учётные данные (401 `INVALID_CREDENTIALS`) → сообщение, интерфейс не открыт.
- O1.3. Превышен лимит попыток (429 `LOGIN_ATTEMPTS_EXCEEDED`) → сообщение о временной блокировке.
- O1.4. Гость с валидной cookie `owner_session` сразу видит элементы управления владельца без входа.

**O2. Шапка / навигация**
- O2.1. Гость без сессии видит ровно две кнопки: «Записаться» и «Админка».
- O2.2. После входа показываются все элементы управления владельца.

**O3. Управление типами событий**
- O3.1. Создание типа события (форма корректна) → `POST /event-types`, тип появляется в списке.
- O3.2. Дубликат slug (409 `DUPLICATE_EVENT_TYPE_ID`) → сообщение, форма не очищается.
- O3.3. Удаление типа события (подтверждение) → `DELETE /event-types/{id}`, тип исчезает из списка.
- O3.4. Ошибка валидации формы (400 `VALIDATION_ERROR`) → текст ошибки рядом с формой.
- O3.5. Создание/изменение/удаление типа события (`POST/PUT/DELETE /event-types`) без сессии владельца → 401 `NO_OWNER_SESSION` (проверяется на уровне недоступности интерфейса).
- O3.6. Редактирование типа события: владелец меняет название/описание/длительность → `PUT /event-types/{id}`, изменения отражаются в списке. Поле `id` (slug) недоступно для изменения.
- O3.7. Собственное расписание доступности типа события: при создании/редактировании владелец включает собственное расписание → в списке появляется бейдж «Собственное», слоты считаются по этому расписанию, а не по расписанию владельца по умолчанию.

**O4. Расписание по умолчанию**
- O4.1. Страница расписания показывает текущее недельное расписание (`GET /schedule`) по дням недели.
- O4.2. Редактирование интервалов и сохранение → `PUT /schedule`, показывается сохранённая версия.
- O4.3. Ошибка валидации при сохранении (400) → текст ошибки, расписание не считается сохранённым.
- O4.4. Открытие страницы расписания без `owner_session` → 401 / интерфейс расписания недоступен.

**O5. Предстоящие брони**
- O5.1. Страница броней показывает предстоящие брони (`GET /bookings`) по возрастанию времени, с гостем и типом события.
- O5.2. Пустой список → понятное пустое состояние.
- O5.3. Владельческий эндпоинт без сессии → 401 (интерфейс броней недоступен).

### Кросс-поток / интеграция
- X1. Гость создаёт бронь → владелец после входа видит эту бронь в списке предстоящих.
- X2. Владелец удаляет тип события, по которому уже есть бронь → бронь сохраняется, новые брони по типу невозможны (404 при попытке записи гостем).
- X3. *(optional / destructive)* Перезапуск бэкенда очищает данные (in-memory) → после рестарта список типов/броней пуст. Выполняется в отдельном worker-процессе или в конце набора, т.к. влияет на порядок тестов.

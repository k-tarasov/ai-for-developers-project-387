## Purpose

Обеспечивает участие агента в командном цикле разработки на GitHub: автоматический ответ и triage в новых issue, создание PR по команде, доработка PR после ревью и регулярные ночные проверки продакшена (Lighthouse) с публичным отчётом.

## ADDED Requirements

### Requirement: Автоматический ответ агента в новом issue

При создании нового issue система SHALL автоматически запустить агента, который проанализирует задачу и оставит в issue ответ: краткое понимание задачи, уточняющие вопросы (если нужны) и/или оценку сложности. Агент SHALL запускаться в среде GitHub Actions без отдельного GitHub App, используя токен репозитория.

#### Scenario: Новый issue без уточнений
- **WHEN** пользователь создаёт новый issue с понятной задачей
- **THEN** workflow запускается по событию открытия issue и агент публикует комментарий с анализом задачи и предложением следующего шага (например, командой `/implement`)

#### Scenario: Новый issue с неоднозначной задачей
- **WHEN** созданный issue содержит неполное или неоднозначное описание
- **THEN** ответ агента включает список уточняющих вопросов и не выполняет реализацию до получения ответов

### Requirement: Создание PR агентом по команде из issue

Система SHALL поддерживать команду в комментарии к issue (например, `/implement`), по которой агент создаёт ветку, вносит правки по задаче и открывает pull request. Созданный PR SHALL содержать описание, связывающее его с issue (например, `Closes #<number>`).

#### Scenario: Команда /implement в issue
- **WHEN** пользователь пишет комментарий `/implement` в открытом issue
- **THEN** агент создаёт отдельную ветку, реализует задачу, коммитит изменения и открывает PR, привязанный к этому issue

#### Scenario: Повторная команда в том же issue
- **WHEN** по issue уже существует открытый PR и пользователь снова пишет `/implement`
- **THEN** агент не создаёт дублирующий PR, а обновляет существующий (сила/пуш в ту же ветку)

### Requirement: Доработка PR после ревью

Система SHALL реагировать на ревью pull request: по команде пользователя агент вносит правки по замечаниям ревью в существующий PR. Доработки SHALL обновлять тот же PR без создания нового.

#### Scenario: Команда доработки после ревью
- **WHEN** на PR оставлены замечания ревью и пользователь запрашивает доработку (комментарий-команда)
- **THEN** агент анализирует замечания, вносит правки в ветку того же PR и пушит их

#### Scenario: Отсутствие открытого PR
- **WHEN** запрошена доработка, но соответствующего открытого PR нет
- **THEN** система отвечает в issue/PR комментарием о том, что PR не найден, и не выполняет изменений

### Requirement: Ночная регулярная проверка продакшена (Lighthouse)

Система SHALL запускать по расписанию (nightly, по крону) проверку продакшн-URL с помощью Lighthouse и публиковать отчёт. Отчёт SHALL сохраняться как артефакт workflow и/или публиковаться в виде комментария или issue с результатами проверки.

#### Scenario: Ночной запуск по расписанию
- **WHEN** наступает время по cron-расписанию workflow
- **THEN** workflow запускает Lighthouse против сконфигурированного продакшн-URL и создаёт отчёт с метриками производительности

#### Scenario: Провал проверки
- **WHEN** Lighthouse-проверка завершается с результатом ниже порога или ошибкой
- **THEN** workflow помечает запуск как неудачный и/или публикует отчёт, указывающий на проблемные метрики, для дальнейшего разбора

#### Scenario: Отсутствие сконфигурированного URL
- **WHEN** продакшн-URL не задан в конфигурации workflow
- **THEN** ночной workflow пропускает проверку или завершается с понятной ошибкой, не блокируя остальные задачи

### Requirement: Изоляция прав workflow

Все workflow-файлы новой capability SHALL запрашивать только минимальные права: `issues: write`, `pull-requests: write`, `contents: write`. Существующие workflow (`ci.yml`, `release-please.yml`, `hexlet-check.yml`) SHALL оставаться без изменений.

#### Scenario: Проверка прав
- **WHEN** инспектируется конфигурация workflow агента
- **THEN** права ограничены перечисленными выше, без лишних scope (например, без `admin` и без `secrets`)

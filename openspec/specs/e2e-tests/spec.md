# e2e-tests Specification

## Purpose
Сквозные (e2e) тесты на Playwright, проверяющие каждый use-case приложения «Запись на звонок» на уровне пользовательских действий в браузере против реального бэкенда (in-memory). Являются источником истины для набора e2e-проверок и отражают сценарии из спеки `frontend-app` и `booking-api`.

## Requirements

### Requirement: e2e-покрытие гостевого потока

Набор e2e-тестов SHALL покрывать гостевой поток: просмотр типов событий, идентификацию/профиль гостя (cookie `guest_id`), просмотр свободных слотов и создание бронирования, включая сценарии ошибок (`SLOT_BUSY`, `SLOT_MISALIGNED`, `SLOT_OUT_OF_WINDOW`, `SLOT_OUTSIDE_SCHEDULE`, отсутствие контакта, `EVENT_TYPE_NOT_FOUND`, недоступность бэкенда).

#### Scenario: Гость видит и выбирает тип события

- **WHEN** новый гость открывает главную страницу
- **THEN** e2e-тест подтверждает отображение списка типов событий, переход по типу и загрузку слотов, сгруппированных по дням

#### Scenario: Гость создаёт бронь с подтверждением

- **WHEN** гость выбирает слот, вводит имя и контакт, добавляет комментарий и отправляет форму
- **THEN** e2e-тест подтверждает вызов `POST /bookings` и экран подтверждения с типом события, временем начала/окончания и комментарием

#### Scenario: Гость обрабатывает ошибки бронирования

- **WHEN** бэкенд отвечает `SLOT_BUSY` или ошибкой валидации слота
- **THEN** e2e-тест подтверждает показ сообщения об ошибке и предложение выбрать другое время

#### Scenario: Неизвестный и знакомый гость

- **WHEN** гость без cookie `guest_id` заполняет форму данных, либо гость с валидной cookie `guest_id` редактирует карточку
- **THEN** e2e-тест подтверждает создание/обновление профиля через `POST /guest`/`PUT /guest` и persistence после перезагрузки страницы

### Requirement: e2e-покрытие владельческого потока

Набор e2e-тестов SHALL покрывать владельческий поток: аутентификацию (`POST /auth/login`, cookie `owner_session`), CRUD типов событий, управление расписанием по умолчанию и просмотр предстоящих броней, включая сценарии ошибок (`INVALID_CREDENTIALS`, `LOGIN_ATTEMPTS_EXCEEDED`, `DUPLICATE_EVENT_TYPE_ID`, `VALIDATION_ERROR`, отсутствие сессии `NO_OWNER_SESSION`).

#### Scenario: Вход владельца и навигация

- **WHEN** владелец вводит корректные учётные данные
- **THEN** e2e-тест подтверждает установку cookie `owner_session`, появление элементов управления владельца и перенаправление в интерфейс владельца

#### Scenario: Владелец управляет типами событий и расписанием

- **WHEN** владелец создаёт, редактирует, удаляет тип события и сохраняет расписание
- **THEN** e2e-тест подтверждает соответствующие обращения к API и отражение изменений в интерфейсе

#### Scenario: Владелец просматривает предстоящие брони

- **WHEN** владелец открывает страницу броней
- **THEN** e2e-тест подтверждает отображение списка броней по возрастанию времени, включая бронь, созданную гостем в рамках того же тестового прогона

### Requirement: e2e-инфраструктура и запуск

e2e-тесты SHALL запускаться против реального бэкенда (in-memory) и фронтенда в тестовом окружении с детерминированными фикстурами (логин владельца, создание типа события, генерация свободного слота). Запуск SHALL быть доступен через npm-скрипт и/или Makefile-цель.

#### Scenario: Запуск e2e-набора

- **WHEN** разработчик выполняет команду запуска e2e (npm script / make target)
- **THEN** поднимается бэкенд и фронтенд, выполняются все e2e-сценарии, результат отчётливо сигнализирует об успехе/провале каждого

#### Scenario: Изоляция данных между прогонами

- **WHEN** выполняется новый прогон e2e
- **THEN** фикстуры создают собственные данные, а перезапуск бэкенда очищает in-memory хранилище, исключая перекрёстное влияние тестов

## Purpose

Веб-интерфейс сервиса «Запись на звонок»: гость бронирует свободные слоты, владелец календаря управляет типами событий, расписанием и просматривает предстоящие брони. Фронтенд обменивается данными с бэкендом только через HTTP API по контракту.

## Requirements

### Requirement: Гость просматривает список типов событий

Фронтенд SHALL отображать гостю список всех типов событий, полученных через `GET /event-types`, с названием, описанием и длительностью каждого типа.

#### Scenario: Список успешно загружен

- **WHEN** гость открывает главную страницу
- **THEN** фронтенд запрашивает типы событий через API и показывает их списком с названием, описанием и длительностью

#### Scenario: Типы событий отсутствуют

- **WHEN** API возвращает пустой список типов событий
- **THEN** фронтенд показывает понятное пустое состояние без ошибки

#### Scenario: Ошибка загрузки списка

- **WHEN** запрос списка типов событий завершился сетевой ошибкой или ошибкой сервера
- **THEN** фронтенд показывает сообщение о недоступности данных и возможность повторить запрос

### Requirement: Гость просматривает свободные слоты типа события

Фронтенд SHALL показывать свободные слоты выбранного типа события, полученные через `GET /event-types/{eventTypeId}/slots`, сгруппированными по дням в пределах окна записи, с указанием границ окна из ответа API.

#### Scenario: Слоты успешно загружены

- **WHEN** гость выбирает тип события
- **THEN** фронтенд запрашивает слоты через API и показывает их по дням в порядке возрастания времени начала

#### Scenario: Свободных слотов нет

- **WHEN** API возвращает пустой список слотов
- **THEN** фронтенд показывает сообщение об отсутствии свободного времени в окне записи

#### Scenario: Тип события не найден

- **WHEN** API отвечает 404 с кодом `EVENT_TYPE_NOT_FOUND`
- **THEN** фронтенд показывает сообщение, что тип события недоступен, и предлагает вернуться к списку

### Requirement: Гость создаёт бронирование

Фронтенд SHALL позволять гостю создать бронирование через `POST /bookings`, передавая выбранный слот, имя, хотя бы один контакт (телефон или email) и необязательный комментарий, и SHALL показывать подтверждение с данными созданной брони.

#### Scenario: Бронирование успешно создано

- **WHEN** гость выбрал слот, заполнил имя и хотя бы один контакт и отправил форму
- **THEN** фронтенд создаёт бронирование через API и показывает подтверждение с типом события, временем начала и окончания

#### Scenario: Не указан ни один контакт

- **WHEN** гость отправляет форму без телефона и без email
- **THEN** фронтенд блокирует отправку и указывает, что нужен хотя бы один контакт, до обращения к API

#### Scenario: Слот занят

- **WHEN** API отвечает 409 с кодом `SLOT_BUSY`
- **THEN** фронтенд сообщает, что слот уже занят, и предлагает выбрать другое время с обновлённым списком слотов

#### Scenario: Слот не проходит валидацию

- **WHEN** API отвечает 400 с кодом `SLOT_MISALIGNED`, `SLOT_OUT_OF_WINDOW` или `SLOT_OUTSIDE_SCHEDULE`
- **THEN** фронтенд показывает текст ошибки из ответа API и предлагает выбрать другой слот

### Requirement: Владелец управляет типами событий

Фронтенд SHALL предоставлять владельцу интерфейс создания, редактирования и удаления типов событий через `POST /event-types`, `PUT /event-types/{eventTypeId}` и `DELETE /event-types/{eventTypeId}`, включая необязательное собственное расписание доступности типа события.

#### Scenario: Тип события создан

- **WHEN** владелец заполняет форму типа события корректными данными и отправляет её
- **THEN** фронтенд создаёт тип события через API и показывает его в списке

#### Scenario: Дубликат идентификатора

- **WHEN** API отвечает 409 с кодом `DUPLICATE_EVENT_TYPE_ID`
- **THEN** фронтенд показывает сообщение, что тип события с таким идентификатором уже существует, и не очищает форму

#### Scenario: Тип события удалён

- **WHEN** владелец подтверждает удаление типа события
- **THEN** фронтенд удаляет тип события через API и убирает его из списка

#### Scenario: Ошибка валидации формы

- **WHEN** API отвечает 400 с кодом `VALIDATION_ERROR`
- **THEN** фронтенд показывает текст ошибки из ответа API рядом с формой

### Requirement: Владелец управляет расписанием по умолчанию

Фронтенд SHALL показывать текущее недельное расписание владельца по умолчанию (`GET /schedule`) и SHALL позволять полностью заменить его (`PUT /schedule`), включая пустые дни как недоступные.

#### Scenario: Расписание отображено

- **WHEN** владелец открывает страницу расписания
- **THEN** фронтенд показывает интервалы рабочего времени по дням недели, полученные через API

#### Scenario: Расписание сохранено

- **WHEN** владелец редактирует интервалы и сохраняет расписание
- **THEN** фронтенд отправляет полное новое расписание через API и показывает сохранённую версию

#### Scenario: Ошибка валидации расписания

- **WHEN** API отвечает 400 при сохранении расписания
- **THEN** фронтенд показывает текст ошибки из ответа API и не считает расписание сохранённым

### Requirement: Владелец просматривает предстоящие брони

Фронтенд SHALL показывать владельцу список предстоящих броней всех типов событий, полученных через `GET /bookings`, по возрастанию времени начала, с данными гостя и снимком типа события.

#### Scenario: Список броней загружен

- **WHEN** владелец открывает страницу броней
- **THEN** фронтенд показывает предстоящие брони с именем гостя, контактами, типом события и временем начала и окончания

#### Scenario: Предстоящих броней нет

- **WHEN** API возвращает пустой список броней
- **THEN** фронтенд показывает понятное пустое состояние

### Requirement: Обращение к бэкенду только по контракту

Фронтенд SHALL получать данные и выполнять действия исключительно через HTTP API, описанный контрактом `spec/main.tsp` (OpenAPI), и MUST NOT содержать иной канал обмена данными с бэкендом (прямой доступ к БД, shared-код с бэкендом, незафиксированные в контракте эндпоинты).

#### Scenario: Все запросы соответствуют контракту

- **WHEN** фронтенд выполняет любое действие с данными
- **THEN** используются только эндпоинты, методы, поля запросов и ответов из действующего OpenAPI-контракта

### Requirement: Работа с отдельно запущенным бэкендом

Фронтенд SHALL корректно работать с бэкендом, запущенным отдельным процессом на настраиваемом адресе (по умолчанию `http://localhost:8080/api`), без совместного развёртывания или общего рантайма.

#### Scenario: Адрес API настраивается

- **WHEN** фронтенд запускается в режиме разработки или собирается
- **THEN** базовый адрес API задаётся конфигурацией окружения, а не зашит в код

#### Scenario: Бэкенд недоступен

- **WHEN** бэкенд не отвечает или недостижим
- **THEN** фронтенд показывает сообщение о недоступности сервера и возможность повторить запрос, интерфейс не «падает»

### Requirement: Режим mock API для разработки

Фронтенд SHALL поддерживать разработку и проверку против mock-сервера, поднятого по OpenAPI-контракту, без запущенного реального бэкенда.

#### Scenario: Запуск против mock-сервера

- **WHEN** разработчик запускает фронтенд в mock-режиме
- **THEN** все запросы направляются на mock-сервер, отвечающий по контракту, и основные сценарии (список типов, слоты, создание брони) воспроизводимы без бэкенда

### Requirement: Владелец проходит аутентификацию

Фронтенд SHALL предоставлять владельцу экран входа и SHALL выполнять вход через `POST /auth/login`, передавая логин и пароль, заданные статически при старте бэкенда. Успешный вход SHALL устанавливать сессию владельца в виде httpOnly cookie, которую бэкенд требует на владельческих эндпоинтах.

#### Scenario: Вход выполнен успешно

- **WHEN** владелец вводит корректные логин и пароль и отправляет форму
- **THEN** фронтенд выполняет `POST /auth/login`, бэкенд возвращает успех и устанавливает сессионную httpOnly cookie владельца, фронтенд открывает интерфейс владельца

#### Scenario: Неверные учётные данные

- **WHEN** владелец вводит неверный логин или пароль
- **THEN** бэкенд отвечает `401` с кодом `INVALID_CREDENTIALS`, фронтенд показывает сообщение о неверных данных и не открывает интерфейс владельца

#### Scenario: Превышен лимит попыток входа

- **WHEN** владелец превысил лимит попыток входа подряд с неверными данными
- **THEN** бэкенд отвечает `429` с кодом `LOGIN_ATTEMPTS_EXCEEDED`, фронтенд показывает сообщение о временной блокировке входа

### Requirement: Шапка с навигацией гостя и владельца

Фронтенд SHALL показывать в головной панели ровно две кнопки: «Записаться» (гостевой поток бронирования) и «Админка» (вход/интерфейс владельца). После успешного входа в админку через форму входа фронтенд SHALL показывать все элементы управления владельца, как в текущем интерфейсе. Если у гостя уже есть валидная сессия владельца (httpOnly cookie `owner_session`), фронтенд SHALL показывать все элементы управления владельца сразу, без повторного входа.

#### Scenario: Гость видит две кнопки в шапке

- **WHEN** гость открывает приложение без сессии владельца
- **THEN** фронтенд показывает в шапке только кнопки «Записаться» и «Админка»

#### Scenario: Переход в админку через форму входа

- **WHEN** гость нажимает «Админка» и успешно проходит вход через форму
- **THEN** фронтенд показывает все элементы управления владельца, как в текущем интерфейсе

#### Scenario: Гость уже админ при открытии

- **WHEN** гость открывает приложение с валидной сессией владельца
- **THEN** фронтенд сразу показывает все элементы управления владельца, форма входа не требуется

### Requirement: Владельческие эндпоинты требуют сессию владельца

Бэкенд MUST требовать сессию владельца (httpOnly cookie из `POST /auth/login`) на всех владельческих эндпоинтах: `POST /event-types`, `PUT /event-types/{eventTypeId}`, `DELETE /event-types/{eventTypeId}`, `GET /schedule`, `PUT /schedule`, `GET /bookings`. Без валидной сессии бэкенд SHALL отвечать `401`.

#### Scenario: Владельческий эндпоинт без сессии

- **WHEN** запрос к любому владельческому эндпоинту приходит без валидной сессии владельца
- **THEN** бэкенд отвечает `401` и не выполняет операцию

#### Scenario: Владельческий эндпоинт с валидной сессией

- **WHEN** запрос к владельческому эндпоинту приходит с валидной сессией владельца
- **THEN** бэкенд выполняет операцию по контракту

### Requirement: Гость идентифицируется по httpOnly-куки

Бэкенд SHALL идентифицировать гостя по httpOnly-куки `guest_id`. `GET /guest` SHALL возвращать профиль гостя (имя и контакты), если куки известна, и SHALL отвечать `404` с кодом `GUEST_UNKNOWN`, если куки отсутствует или неизвестна. `POST /guest` SHALL создавать или идентифицировать гостя по переданным имени и контактам и флагу `rememberMe`; при `rememberMe=true` бэкенд SHALL выдать `guest_id` со сроком 30 дней, иначе — сессионную куки. `PUT /guest` SHALL обновлять профиль знакомого гостя.

#### Scenario: Известная куки возвращает профиль

- **WHEN** бэкенд получает `GET /guest` с известной куки `guest_id`
- **THEN** бэкенд возвращает профиль гостя с именем и контактами

#### Scenario: Неизвестная куки

- **WHEN** бэкенд получает `GET /guest` без куки или с неизвестной куки
- **THEN** бэкенд отвечает `404` с кодом `GUEST_UNKNOWN`

#### Scenario: Гость создан с запоминанием

- **WHEN** фронтенд отправляет `POST /guest` с `rememberMe=true`
- **THEN** бэкенд создаёт/идентифицирует гостя и выдаёт `guest_id` со сроком 30 дней

#### Scenario: Гость создан без запоминания

- **WHEN** фронтенд отправляет `POST /guest` с `rememberMe=false`
- **THEN** бэкенд создаёт/идентифицирует гостя и выдаёт сессионную куки `guest_id`

#### Scenario: Профиль знакомого гостя обновлён

- **WHEN** фронтенд отправляет `PUT /guest` с изменёнными данными и валидной куки `guest_id`
- **THEN** бэкенд обновляет профиль гостя и возвращает обновлённые данные

### Requirement: Главная страница загружает профиль гостя

Фронтенд SHALL запрашивать профиль гостя через `GET /guest` при открытии главной страницы. Если бэкенд отвечает `404 GUEST_UNKNOWN`, фронтенд SHALL считать гостя неизвестным и показать поток ввода данных; если профиль получен, SHALL показать карточку знакомого гостя.

#### Scenario: Гость известен

- **WHEN** `GET /guest` возвращает профиль
- **THEN** фронтенд показывает карточку знакомого гостя с его именем и контактами

#### Scenario: Гость неизвестен

- **WHEN** `GET /guest` отвечает `404 GUEST_UNKNOWN`
- **THEN** фронтенд показывает интерфейс для неизвестного гостя (выбор длительности и форму данных)

#### Scenario: Ошибка загрузки профиля гостя

- **WHEN** запрос `GET /guest` завершился сетевой ошибкой или ошибкой сервера
- **THEN** фронтенд показывает сообщение о недоступности данных и возможность повторить запрос

### Requirement: Неизвестный гость заполняет форму после выбора длительности

Фронтенд SHALL, для неизвестного гостя, после выбора желаемой длительности (типа события) показывать форму с полями имя и контакты и галочкой «запомнить на 30 дней», и SHALL отправлять данные через `POST /guest` с флагом `rememberMe`, равным состоянию галочки.

#### Scenario: Форма отправлена с запоминанием

- **WHEN** неизвестный гость выбрал длительность, заполнил имя и контакт и отметил «запомнить на 30 дней»
- **THEN** фронтенд отправляет `POST /guest` с `rememberMe=true` и после успеха переводит гостя в состояние «знакомый»

#### Scenario: Форма отправлена без запоминания

- **WHEN** неизвестный гость заполнил форму без отметки «запомнить на 30 дней»
- **THEN** фронтенд отправляет `POST /guest` с `rememberMe=false`

#### Scenario: Не указан ни один контакт

- **WHEN** гость отправляет форму без телефона и без email
- **THEN** фронтенд блокирует отправку и указывает, что нужен хотя бы один контакт, до обращения к API

### Requirement: Знакомому гостю показывается редактируемая карточка

Фронтенд SHALL показывать знакомому гостю на главной странице карточку с именем и контактными данными, которые гость может изменить на месте, и SHALL сохранять изменения через `PUT /guest` с валидной куки `guest_id`.

#### Scenario: Данные карточки изменены и сохранены

- **WHEN** знакомый гость редактирует имя или контакт в карточке и сохраняет
- **THEN** фронтенд отправляет `PUT /guest` и показывает обновлённую карточку

#### Scenario: Сохранение карточки завершилось ошибкой

- **WHEN** `PUT /guest` отвечает ошибкой
- **THEN** фронтенд показывает текст ошибки и не считает данные сохранёнными

### Requirement: Гость выбирает событие и открывает компонент просмотра с комментарием

Фронтенд SHALL показывать под карточкой/формой гостя список выбираемых типов событий; переход по событию SHALL открывать компонент с информацией о событии, календарём и слотами времени, где гость может добавить комментарий, который включается в создаваемую бронь (`POST /bookings`, поле `guestComment`).

#### Scenario: Список событий под карточкой

- **WHEN** знакомый гость видит главную страницу
- **THEN** под карточкой фронтенд показывает список типов событий, полученный через `GET /event-types`

#### Scenario: Переход открывает компонент события

- **WHEN** гость выбирает событие из списка
- **THEN** фронтенд открывает компонент с описанием события, календарём и слотами (`GET /event-types/{eventTypeId}/slots`)

#### Scenario: Гость добавляет комментарий к брони

- **WHEN** гость заполняет поле комментария в компоненте события и создаёт бронь
- **THEN** фронтенд включает комментарий в `POST /bookings` (поле `guestComment`)
